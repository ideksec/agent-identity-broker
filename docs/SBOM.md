# Software Bill of Materials

What the `sbom` workflow (`.github/workflows/sbom.yml`) produces, what it
gates on, where to find the output, and where AI fits.

## What is produced

Every push, pull request and Monday morning (UTC) the workflow uploads these
artifacts to the run:

| Artifact | Contents | Generated by |
|---|---|---|
| `sbom-source` | `agent-identity-broker.source.cdx.json` — CycloneDX 1.6 SBOM of every third-party Python package in `uv.lock`; alongside it, `requirements.lock.txt`, the hashed export it was generated from (cyclonedx-py does not carry `--hash` values into the SBOM, so the export is the hash record) | `cyclonedx-py` from `uv export --locked` |
| `sbom-image-<name>` | `<name>.cdx.json` and `<name>.spdx.json` — Python packages, Debian packages and the image itself, for each of `broker`, `mock-idp`, `demo-agent` | Syft, against an image built from the lockfile |
| `sbom-deployment` | `deployment.cdx.json` — the third-party images, base images and Helm charts the repo deploys, read from `deploy/`, `*/Dockerfile` and `scripts/install-spire.sh`; plus a Syft SBOM per third-party image | `scripts/deployment-bom.py`, Syft |

The workflow's single source of truth is `uv.lock`. The Dockerfiles install
from it, CI tests against it, and the source SBOM is exported from it, so the
three views describe the same resolved set.

## What fails the build

- **Any known advisory** against the lockfile (`pip-audit`, source-sbom job).
  The set is clean as of the commit that introduced this workflow. The weekly
  run exists so a newly published advisory turns the workflow red without
  anyone pushing.
- **Critical vulnerabilities with a fix available** in our own three images
  (Grype, image-sbom job). Grype results are also uploaded to the repository's
  code-scanning tab. The threshold is the `GRYPE_SEVERITY_GATE` variable at
  the top of the workflow; the intent is to tighten it to `high` once
  `python:3.12-slim` is pinned by digest.

Third-party images (`postgres:16`, `openpolicyagent/opa:0.70.0`) are SBOMed
and scanned for visibility but not gated — fixes come from upstream, and the
right response is bumping the tag in `deploy/k8s/`.

## Publishing and attestation (opt-in)

Set the repository variable `PUBLISH_IMAGES` to `true` and pushes to `main`
will also publish the three images to
`ghcr.io/<owner>/agent-identity-broker/<name>` and attach a signed SBOM
attestation to each pushed digest. Verify one with:

```bash
gh attestation verify oci://ghcr.io/<owner>/agent-identity-broker/broker:<sha> --owner <owner>
```

Nothing is published while the variable is unset.

## Regenerating locally

```bash
uv export --locked --all-packages --no-dev --no-emit-workspace \
  --format requirements-txt -o requirements.lock.txt
uvx --from cyclonedx-bom cyclonedx-py requirements requirements.lock.txt \
  --of JSON --sv 1.6 -o source.cdx.json
uvx pip-audit -r requirements.lock.txt --no-deps

python3 scripts/deployment-bom.py -o deployment.cdx.json
```

Image SBOMs need Docker and Syft: build with the repo root as context
(`docker build -f broker/Dockerfile .`) and run `syft docker:<image>`.

## Where AI fits

There are no AI components in this codebase in the sense the AI BOM
standards describe: no models, no weights, no inference endpoints, no prompts,
no agent framework, no MCP server. The CycloneDX ML-BOM component types
(`machine-learning-model`, `data`, model cards) and the SPDX 3.0 AI and
Dataset profiles have nothing here to describe, so no AI BOM is produced —
an empty one would only imply otherwise.

What this system *is* is an identity and authorization layer for AI agents.
The inventory that matters for it is the inverse of a conventional AI BOM:
which agents exist, who owns them, what they are entitled to, what policy
governs them and what credentials they can obtain. Today that lives in three
places that can drift — the OPA data ConfigMap (`agents.yaml`), the SPIRE
`ClusterSPIFFEID` templates in `deploy/helm-values/spire-values.yaml`, and
the broker's `agents` table. There is no ratified standard for an agent BOM
yet. When it is produced, the broker is its natural emitter, since the broker
is the system of record; the plan is a `GET /v1/bom/agents` endpoint that
renders the registry as CycloneDX `application` components with properties.

This becomes a conventional AI BOM concern at **Phase 5**, when the MCP
Gateway lands: MCP servers and their tool definitions are model-facing
surfaces that belong in an AI BOM, and the deployment BOM script is where
they should be added.
